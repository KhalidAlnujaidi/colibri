2Scaling — the plateau

The speedup does not keep growing with token count — it plateaus at ~1.4–1.5×. That is exactly what you'd expect when the win is a constant per-frame cost, not a growing one: C/C++ sit ~0.70 µs per DATA frame vs Python ~0.99 µs, and that fixed per-token ratio is what the aggregate speedup converges to. There is no superlinear blow-up in Python's frame loop to exploit at scale.

3Absolute glue cost stays small

Even at 64,000 tokens/req, the entire orchestration round-trip through fork/exec pipes is only ~45 ms in C and ~63 ms in Python — the vast majority of that is moving 192 KB of frame bytes across the pipe, which real inference would dwarf. At 64,000 tokens the throughput difference is C 22.3 req/s vs Python 15.8 req/s (C++ 22.0 req/s). The orchestration layer is not the bottleneck in absolute terms; the wins compound as capacity at the gateway boundary under many concurrent turns.

4Method

Isolating orchestration only. All three drivers talk to the same compiled C stub_engine (identical protocol: READY, then per request a SUBMIT <id> <slot> <bytes> <max> <t> <p> header + prompt, then N DATA <id> <n>\n…\n frames and a DONE line). One persistent engine process is reused across iterations — the coli serve "service" regime. req/s = 1e6 / median; warm-up run first. Token bytes are streamed to /dev/null (as SSE would emit them) so tables stay readable. Build: clang -O2 (C), clang++ -O2 -std=c++17 (C++), python3. At 64000 tokens the C/C++ drivers clamp their minimum to 10 iters (requested 5); Python used 5 — both give stable medians. macOS/arm64.
